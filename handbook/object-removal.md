# Retiring dependent database objects

Run `moon run engine/cli -- specimens/retire-objects.sql --transaction=autocommit --delivery=statements --sarif`. The project-owned example inventories common removal operations before execution by an external migration runner. The review never drops database objects.

The profile accepts DROP VIEW/MATERIALIZED VIEW/SEQUENCE/TYPE/DOMAIN/SCHEMA/EXTENSION and FUNCTION/PROCEDURE, optional IF EXISTS, 1–32 targets and optional CASCADE/RESTRICT, at most 512 tokens. Schema and extension names are unqualified. Routine targets require explicit signatures (including empty `()`), with 0–32 bounded type arguments; argument names/modes, arrays and arbitrary signatures remain incomplete. DROP TRIGGER/POLICY accepts one unqualified object name ON one bounded qualified table. Extra clauses and unsupported object types, including database/role removal, remain incomplete rather than being silently ignored.

PG631 covers the removed application/database contract and absence-only IF EXISTS semantics. PG632 treats recursive CASCADE as an error requiring inspection: type/domain removal can delete dependent columns, schema/extension removal can delete data and cross-schema members, and view/routine dependencies can propagate. PG633 retains unresolved ownership, overload, dependencies and lock sets. No dependency graph, missing-object certainty or recovery SQL is fabricated. RESTRICT does not preserve the target or owned/member objects, and rollback before commit differs from recovery after committed data loss.

PG634 tracks the owning-table ACCESS EXCLUSIVE lock for trigger/policy deletion through renames and savepoints. PG635 distinguishes policy removal from disabling RLS: the last removed policy with RLS still enabled means default-deny for non-bypass users, while other permissive/restrictive policies can change access differently. **DROP POLICY CASCADE/RESTRICT have no effect** and do not get a false cascading-object diagnostic. PG636 warns about lost trigger integrity/audit/replication behavior. PG637 covers sequence counter/ownership/default loss; recreating the same name does not restore state. PG638 calls out materialized/contained data and grants. No lock on an unidentified dependent relation is invented.

`engine/object_removal_test.mbt` covers exact grammar, signature/list limits, policy exceptions, transaction/savepoint lock restoration, truncated input, retained source, deterministic exports and strict replay. `checks/postgres.mbtx` checks real overload selection, type/sequence dependency loss, trigger/policy locks and non-bypass policy behavior on disposable objects.
